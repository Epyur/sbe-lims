# Дизайн: аналогичные объекты для статистики отчёта — материал вместо ЕКН

Дата: 2026-10-17. Статус: согласован (все развилки решены пользователем),
готов к плану реализации.
Сервис: `lab-service` (ветка `backend`) + `sbe-ekn`/`ekn-service` (источник признаков).
Клиент `sbe-lims` не меняется.

## Задача

Сейчас «аналогичный объект» в приложении ИИ-отчёта — заявка с **тем же ЕКН объекта**
и тем же методом (`report_context.go`, `loadAnalogueRequests`:
`WHERE r.method_id = $1 AND r.ekn = $2`). ЕКН — это артикул конкретной **фасовки**:
один и тот же материал выпускается рулоном 2,10×20, 2,10×25, 2,10×33 м, плитой
2385×1185 или 2400×1200 мм, в сером / белом / хаки цвете. Каждая комбинация — свой
ЕКН, поэтому аналоги собираются только внутри одной фасовки, а статистика по
материалу не складывается вовсе.

Живые цифры на базе `lab` (2026-10-17): 682 заявки, ЕКН заполнен у **69** из них
(21 уникальный), у объектов — 123 из 350. То есть текущий механизм практически не
работает: для большинства заявок приложение отчёта пустое.

Требуется: определять аналогичность **по материалу**, толщину при этом считать
характеристикой внутри группы, а не признаком тождества, и показывать в отчёте
зависимость показателей от толщины.

## Решения (утверждены пользователем 2026-10-17)

Идентичность материала (ключ):

```
материал = (тип материала, линейка, модификатор)
```

| Признак | Входит в ключ | Решение |
|---|---|---|
| Тип материала (ПВХ-мембрана, плиты, герметик) | **да** | по карточке ЕКН |
| Линейка (Logicroof V-RP, LOGICPIR PROF, Ecoplast V-RP) | **да** | по карточке ЕКН / названию |
| Модификатор (FR, Pro, Arctic, Полы ФЛ/ФЛ, Ф/Ф) | **да** | часть названия линейки |
| Толщина | **нет** | **все толщины одной линейки — один материал**; различаются в анализе |
| Фасовка (ширина × длина, габарит плиты) | нет | никогда не важна |
| Цвет | нет | никогда не важен |
| Торговые названия-двойники (Ecoplast / ECOROOF / TSTN) | — | **разные материалы** |
| Модификаторы (FR / Pro / Arctic) | — | **разные материалы** |

Толщина не только не входит в ключ, но и **не анализируется в отчёте отдельной
ступенью**: она становится измерением внутри группы («закономерности при изменении
толщины»).

Ступени аналогичности в приложении отчёта:

| Ступень | Условие | Подпись |
|---|---|---|
| 1 | ключ совпал, ЕКН у аналога заполнен | «Тот же материал, другая фасовка / толщина» |
| 2 | ключ совпал по названию, ЕКН у аналога пуст | «ЕКН не указан — определено по названию» |
| 3 | та же базовая линейка, другой модификатор | «Модификация линейки (FR / Pro / …)» |

Ступени **не смешиваются** в статистике: ступень 1 — основной анализ, ступень 2 —
отдельная таблица (данные, но без ЕКН), ступень 3 — справочно, отдельным блоком.

Порог для текстового вывода о тренде: **≥ 3 испытания на толщину**.

Мусорный ЕКН (в поле записано название с номером, например
`ПВХ Ecoplast V-RP 1.2 мм мембрана серая 2.10х25, 591278`) — вытаскивать последний
шестизначный числовой хвост, лечить; если не удалось — определять по названию.

## Архитектура

### Часть A — разбор признаков материала (чистые функции)

Новый файл `lab-service/material_key.go` — **без БД и сети**, целиком
юнит-тестируемый:

```go
// MaterialKey - идентичность материала для отбора аналогов.
type MaterialKey struct {
    Type      string // roofing_polym_membr, pvc, теплоизоляционные плиты, ...
    Line      string // "logicroof v-rp" (нормализованная строка)
    Modifier  string // "fr", "pro", "arctic", "полы фл/фл", "" - нет
}

// ParseMaterialFromName - разбор названия объекта/"name_web" методом регулярки
// + нормализации. Возвращает ключ и толщину (0 - не определена).
func ParseMaterialFromName(raw string) (MaterialKey, float64)

// ParseMaterialFromFeatures - ключ и толщина из структурированной карточки ЕКН.
func ParseMaterialFromFeatures(f EknFeatures) (MaterialKey, float64)

// NormalizeMaterialKey - приведение к канонической форме для сравнения
// (снятие омоглифов, схлопывание пробелов/разделителей, единый регистр).
func NormalizeMaterialKey(k MaterialKey) MaterialKey
```

Работа `ParseMaterialFromName`:

1. **Нормализация** (общая, до разбора): Unicode NFKC; кириллические омоглифы в
   латинских словах → латиница (а/е/о/р/с/х/у/к/м/т/в/н); `_` и `-` в
   номере модели → `-`; `х` в габаритах → `x`; пробелы схлопнуть; регистр → нижний.
   Это чинит `Lodgicroof`, `V_RP`, `Arctiс`, `2385х1185`.
2. **Удаление шума**: хвосты `№п.NNNN`, партии `лот#`, `партия NNNN`, цветовые и
   размерные фрагменты (`1,5 мм`, `2,10x20 м`), мусор в конце (`сурьма RG-69`,
   `15% пластикат`).
3. **Модификатор**: словарь известных (`FR`, `Pro`, `Arctic/Арктик`, `Полы ФЛ/ФЛ`,
   `Ф/Ф`, `Middle` — см. решение ниже) + то, что осталось от линейки.
4. **Линейка** — оставшийся латинский/буквенный блок модели (`Logicroof V-RP`,
   `LOGICPIR PROF`, `Ecoplast V-RP`). Разделитель «тип + линейка» (`ПВХ`,
   `Плиты теплоизоляционные`, `TSTN`) отрезается по словарю типов.

**`Middle` — это модификация (решение пользователя 2026-10-17).** В живых данных
`Logicroof V-RP Middle` / `Logicroof Middle V-RP` встречается десятки раз
(объекты 1007–1019, 1022–1029, 1038–1044, 1057–1073), при этом у ЕКН-карточек
`Middle` в названии нет вовсе. **`Middle` — отдельный материал**: он входит в
ключ как `modifier = "middle"`, такие заявки показываются **ступенью 3**
(«Модификация линейки»), то есть в строгую статистику не попадают. Позиция слова
в названии не важна — `Logicroof Middle V-RP` и `Logicroof V-RP Middle` дают
один и тот же ключ.

### Часть B — карточка ЕКН и кэш признаков

```sql
CREATE TABLE IF NOT EXISTS ekn_material_features (
  ekn         TEXT PRIMARY KEY,
  type        TEXT NOT NULL DEFAULT '',
  line        TEXT NOT NULL DEFAULT '',
  modifier    TEXT NOT NULL DEFAULT '',
  thickness   DOUBLE PRECISION,          -- NULL - не определена
  width_m     DOUBLE PRECISION,
  length_m    DOUBLE PRECISION,
  color       TEXT NOT NULL DEFAULT '',
  source      TEXT NOT NULL DEFAULT '',  -- qrc | name | manual
  fetched_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

- Заполняется по требованию: при первом использовании ЕКН в отчёте — запрос
  `ekn-service`, разбор, запись. Дальше — из кэша без сети.
- Отдельно от кэша `ekn`-базы: там TTL 7 дней и сырой дамп, здесь — разбор для
  отчётов (переживает рестарты и недоступность ekn-service).
- Порча/устаревание: `fetched_at` + ручная перезапись (`source='manual'`) для
  случаев, когда QRC не дал признаков, а пользователь знает материал. Ручки
  ручной правки в v1 **не делаем** (границы).

`ekn_client.go`: `lookupEknProductName` переиспользуется как есть;
новый `lookupEknFeatures(ctx, ekn) (EknFeatures, error)` — тот же сетевой путь
(`GET /api/ekn/product/{ekn}`), разбор `data.groups` в структуру `EknFeatures`:

```go
type EknFeatures struct {
    NameWeb   string
    TypeMat   []string // Modif.atr_type_material
    TypeOfGid string   // Modif.type_ofgidro.data
    Thickness float64  // Thickness.value.amount (мм), 0 - нет
    Width     float64  // мм, 0 - нет
    Length    float64  // мм, 0 - нет
    Color     string   // Spec.atr_color_material.data
    Armature  string   // Spec.armirovanie.data
}
```

Разбор QRC-JSON — чистая функция (`parseEknFeatures(map[string]any) EknFeatures`),
тестируется на **снятых в эту сессию реальных ответах** (фикстуры в тестах).

### Часть C — отбор аналогов

`report_context.go`:

- `resolveRequestMaterial(ctx, req)` → `MaterialKey` + толщина + источник
  (`ekn` / `name`). Приоритет: `requests.ekn` (с лечением мусора) → `objects.characteristics.ekn`
  → разбор названия объекта → разбор `requests.title`.
- `loadAnalogueRequests` — вместо `r.ekn = $2`:
  - SQL выбирает **все заявки того же метода** (без фильтра ЕКН), с полями
    `ekn`, `object_id`, `title`, `object.name`, `characteristics` (батч, LIMIT
    с запасом — `maxAnalogues` уже есть, но теперь фильтрация после разбора
    в памяти, поэтому LIMIT поднимаем до 2000 и сортируем по дате завершения);
  - в памяти — ключ материала каждой заявки (через кэш признаков), сравнение с
    ключом текущей; результат раскладывается по трём ступеням.
  - Один отчёт = один проход по заявкам метода. При 682 заявках и 350 объектах
    это сотни разборов названий — дёшево (regexp), сетевые запросы только за
    ЕКН-карточками, отсутствующими в кэше.

Результат — `[]analogueRow` с новым полем `Tier` (`1|2|3`) и `MaterialLabel`
(человекочитаемая расшифровка ключа для отчёта).

### Часть D — статистика с разрезом по толщине

`computeIndicatorStats` получает признак толщины аналога и возвращает **два
уровня**:

```go
type indicatorStat struct {
    ID, Name string
    Count    int
    HasNumeric bool
    Avg, Min, Max float64
    Distribution map[string]int
    ByThickness []thicknessStat `json:"by_thickness,omitempty"`
}

type thicknessStat struct {
    Thickness  string  // "1,2", "1,5", "не указана"
    Count      int     // значений показателя
    Tests      int     // различных испытаний (заявок)
    Avg, Min, Max float64
    Distribution  map[string]int
    HasTrend   bool    // Tests >= 3
}

type trendNote struct {
    IndicatorID string
    Direction   string // "растёт" | "падает" | "не меняется" | "немонотонно"
    From, To    string // "1,2" → "2,0"
    Delta       string // "+12%" / "−8%"
    Confidence  string // "данных достаточно" | "данных мало"
}
```

Правила:

- Срез — по толщине (мм, округление 0,1). Толщина не определена → строка
  «не указана», в тренд не входит.
- **Тренд считается только при ≥ 3 испытаниях на толщину** (решение
  пользователя 2026-10-17). Если хотя бы у одной толщины меньше — `HasTrend=false`,
  в отчёте — только цифры, без текстового вывода.
- **Сравнение внутри разброса.** Разброс задаётся срезом по толщине, который
  попадает в сравнение. При `3+` испытаниях средние — это средние, а не диапазон
  от минимума до максимума, поэтому сравнение идёт по `avg`, и правило
  «немонотонно» срабатывает только на смене знака приращения (среднее сначала
  выросло, потом упало). Пересечение `[min..max]` соседних толщин при 3+ испытаниях
  тренда не отменяет (решение пользователя 2026-10-17):
  - направление считается по знаку приращения среднего между крайними толщинами на
    всей оси (1,2 → 1,5 → 2,0): если знак одинаков — «растёт»/«падает»;
  - смена знака хотя бы на одном шаге — «немонотонно», текстового вывода нет.
- ИИ **не считает** тренд — он получает уже посчитанные `ByThickness`/`trendNote`
  и пишет по ним текст (`renderReportContext` дополняется разделами).

### Часть E — приложение в отчёте

`composeAppendixNodes` собирает:

1. **Заголовок**: «Приложение. Статистика по аналогичным объектам» + расшифровка
   материала: «Линейка: Logicroof V-RP · тип: полимерная ПВХ-мембрана ·
   модификатор: —».
2. **Таблица ступени 1 — свод по показателям** (как сейчас: count/avg/min/max +
   распределение).
3. **Таблицы ступени 1 — по толщинам (решение пользователя 2026-10-17: мини-таблицы,
   по одной на показатель).** Для каждого показателя — отдельная маленькая таблица:
   строки = толщины, колонки = «Испытаний / Серий / Среднее / Мин / Макс» (для
   нечисловых — «Испытаний / Распределение»). Рядом или под таблицей — строкой
   `trendNote`, если он есть. Одна широкая таблица со склейкой заголовков
   отвергнута: при 6+ показателях она нечитаема в DOCX.
4. **Вывод о закономерностях** — текстом: сгенерированные ИИ разделы + (при
   отсутствии ИИ) детерминированная строка из `trendNote`.
5. **Таблица «Аналоги»** — как сейчас (`analogueRow`), но с колонками
   «Линейка / толщина / фасовка / цвет» и пометкой ступени.
6. **Ступень 2** (без ЕКН) и **ступень 3** (модификации) — отдельными
   таблицами с явной подписью.

## Что НЕ входит (границы v1)

- Ручная правка признаков материала (`source='manual'` в таблице зарезервирован,
  но UI и ручки не делаем).
- Пересборка отчётов задним числом по новому правилу — не делаем; новый отбор
  применяется к новым сборкам, старые сохранённые отчёты не трогаются.
- Разбор по фотографии/PDF стандарта — нет.
- Анализ по цвету — сознательно исключён (решение пользователя).
- Модификаторы вне известного словаря — в v1 попадают в `Line` как есть
  (то есть становятся частью линейки), а не в `Modifier`.

## Открытые вопросы

Все три развилки закрыты пользователем 2026-10-17 — открытых вопросов нет:

1. **`Middle`** — отдельная модификация (`modifier = "middle"`), заявки уходят
   **в ступень 3** («Модификация линейки»), из строгой статистики исключаются.
2. **Тренд при пересечении разброса** — считается по средним, при 3+ испытаниях на
   толщину; отменяется только сменой знака приращения («немонотонно»).
3. **Форма таблицы по толщинам** — **мини-таблица на каждый показатель**
   (одна широкая отвергнута).
